这份说明回答四个问题：① 这套系统能做什么、做不到什么 → ② 一条内容在里面是怎么走的 → ③ 要复刻得准备些什么、人怎么分工 → ④ 以后想做实时预警，该往哪个方向走。代码和环境那部分已经打包交付了，这里讲的是项目层面的事——不需要技术背景，需要的是业务判断和人手安排。

①这套系统能做什么、做不到什么

这套系统在我们公司连续跑了 4 个月。它要解决的不是"信息不够"，而是三件一直没解决好的事：信息又多又漏——公众号一天几百条，真正相关的只有两三条，而该知道的那条偏偏没人刷到；东西留不下来——有价值的信息躺在各人的收藏夹和群聊里，人一走就带走了；看起来太费劲——发到群里没人有时间读，大家真正想知道的是"这条跟我有什么关系、我要不要做点什么"。

Before · 人去找信息

  • 每个部门自己上网搜，费时费力还容易漏
  • 剩下的靠人脉打听、靠平台推荐——刷到什么算什么
  • 同行动作、政策变化、客户投诉：等自己听说的时候，往往已经晚了
  • 各自存在各自手里，散在群聊里，攒不下来也没法复用

Now · 信息来找人

  • 按监控词去多个平台定向采、批量采
  • AI 拿事先写好的标准逐条读、打标签、分等级，跟我们无关的直接滤掉（大约占一半）
  • 整理完直接送到各部门的看板，高危的置顶提醒
  • 全部存进库里，每条都能翻回原文；标准越校越准

能力边界：它做不到什么（复刻前先知道）

下面六条不是列缺点，是把设计上做过的取舍讲清楚。有人问"这系统是不是全自动、是不是实时的"，答案都在这里。

1它不是实时的

采集是定时成批跑的，而且要有人点一下才开始，不会自己在后台一直转。一条帖子从发出来到进看板，通常是几小时到一两天。

想把这个时间缩短到分钟级，路径和投入我整理在 第 ④ 章「实时预警」↓。先说结论：对小红书做"秒级"不现实，市面上的商用工具也做不到。

2小红书这一路有平台限制

登录状态过几天就失效，要人重新扫码；帖子的原文链接也是过几天就打不开。所以系统在采集当时就把正文原样存下来了——哪怕以后原帖链接失效，内容照样能在系统里看到，不用担心"点进去是空的"。

这是平台自己的规则，不是系统做得不好。反过来说，任何号称"能永久稳定全自动采小红书"的方案，都值得多问几句。

3公众号这一路是"搜"来的，不是"订"来的

系统不是像订阅号那样自动收全某个号的新文章，而是拿监控词去搜——搜到哪些算哪些，总会有漏掉的，而且搜回来的以旧文章居多。

所以监控词表写得好不好，直接决定这一路能拿回多少东西——这也是词表被列进"三件套"的原因（见 ③）。想更全，可以看这个开源工具 wechat-article-exporter↗：用自家公众号后台的身份把订阅的号整个导出来。我试过 48 个号、496 篇文章一次成功，结论是可行，但要配一套扫码和限速的规矩。

4高危舆情绝不自动往外发

判定为高危的帖子，系统只把研判卡放进门户的预警区，停在那里等人看，不会自动推给任何群、任何人。这是故意这么设计的。

三个原因：AI 会判错；品牌声誉的事必须有人签字负责；自动发错一次的代价，远大于晚十分钟发出来。这一条建议原样保留。

5门户只能在公司内网用

后台接口没有做登录校验，所以绝对不能映射到公网上；页面上那个邀请码只是一道门帘，防的是误入，防不住懂技术的人绕过去。

三条部署红线：只在公司可信内网里跑；不要把敏感个人信息放进去；如果确实需要真正的登录校验，得请 IT 在服务端加一层。

6AI 的判断有已知的盲点

比如商家的官方账号、销售人员发的广告贴，系统目前还分不出发帖的是不是卖方，会把它们当成普通用户的真实声音收进来。这块正在改。

判定标准需要人一直校准下去——这套系统的上限不在技术，在判定标准写得准不准。有人手能持续做这件事，价值很大。

三件套长什么样：填空示范

复用包里这三样都是 {{占位符}} 模板。下面各给一个"模板原样 vs 填好的样子"对照——医院板块那一栏是我随手写的示意，实际以你们自己的说法为准；我们那一栏是真实在跑的内容。

{{一句话写清什么不归你们管——这条是滤掉不相干内容的关键}}
✅ 填好的样子（医院板块版 · 示意） 「这家医院是高端私立综合医疗集团，为家庭客户提供妇产、儿科、全科到专科的全周期服务。」
业务线：妇产 / 儿科 / 全科与专科 / 体检 / 保险直付服务
竞品：你们真实对标的 2–3 家高端私立机构（写具体名字）
不做什么：「不评价公立体系诊疗水平；不收医美纠纷类内容；不收与本院无关的医患矛盾时政讨论。」

中文版是给人看、以后也靠它维护；英文版（company-context.md）才是 AI 跑起来时真正读的那份——内容一样，逐条翻过去就行（可以让 AI 帮你翻，人再核一遍）。例：We do NOT: comment on public-hospital care quality; …。两份的空格数不一样（中文大约 49 处、英文大约 35 处）不用在意——装的是同一套信息，只是详略和格式不同，以中文版为准先填完，再对照翻译，验收都是同一条：全局搜 {{ 一个不剩。⚠️ 两份内容对不上，AI 就会按旧的那份判——这是最不容易被发现的一种失准。

示范 3 · 部门判定标准——先猜、后校准，两个阶段

判定标准有专门一份文档记录（复用包内 templates/dept-routing-criteria-template.md；我们在跑的对应文件是《部门判定标准·定稿池》，问卷每收一份就固化一节）。AI 每次判读，都是把这份文档拼进 Prompt 执行——所以"改标准"就是改这份文档。

第一阶段 · 起步版：我和 AI 一起猜

还没有任何问卷时，我和大模型逐个部门脑暴"他们应该关心什么"，写进文档先跑起来。当时实际喂给 AI 的判定段落长这样（节选示意，真实文件长得多）：

📄 分流 Prompt 节选 · 第一阶段（猜的版本） 【分给哪个部门】读完这条内容，判断它主要该给哪个部门（只能选一个）：
· HR —— 用工政策、社保新规、员工福利变化 ← 我猜的
· 医疗网络 —— 凡提到「预授权」的内容都归这里 ← 我猜的
· 市场渠道 —— 品牌口碑、同业营销活动、渠道动作
· ……（每个部门下面列正例 ✓ / 反例 ✗，AI 按例子类推）

诚实交代：截至 7 月底问卷只回收了 4/15 份——没答卷的部门，今天仍在用这种猜的版本跑。第一版不怕猜错，怕不上线：不上线，就永远没有可以让同事批改的实物。

第二阶段 · 校准版：发问卷收真话，回来改 Prompt

问卷怎么问有讲究，三条原则：回溯（问"上次因为外面的消息改变做法是什么时候"，不问"你希望看到什么"——人对已发生的事记得准，对未来的想象不准）；批改（把我猜的标准预填好，让同事打勾或划掉，比空白填空回收率高得多）；举例（每人 2 条想要 + 1 条不想要的真实例子，"不想要"比"想要"值钱）。

一份答卷从收回到生效是这样走的——HR 域真实过程：

  1. 猜的版本在出什么错：按第一阶段的标准，「社保缴费基数调整解读」这类宏观政策文源源不断进 HR 看板——打开一看，全是读了也没法行动的新闻
  2. 问卷收回真话：HR 同事把"用工政策 / 社保新规"整行划掉，写下原话：「我要的是具体到某家同业公司的人事动静——裁员、搬迁、组织调整，那是我去挖人的时机」
  3. 回来改那一行 Prompt：改成「只收点名具体同业公司的人事信号；宏观政策类直接过滤」。改完后，同类内容的走向立刻不同——「社保新政解读」→ 过滤，不再打扰；「某同业公司华南区裁员」→ 进 HR 看板、标高价值

同款校准另一例：「预授权」类内容原先全给医疗网络（猜的），预授权、运营两个部门的答卷交叉印证后拆成两半——审核/时效口径 → 医疗网络；被卡/结算卡壳 → 理赔运营。校准不是推倒重来，是一行一行换血：每收一份问卷，就把那个域从"猜的"换成"同事亲口说的"。

两条路：从零编 vs 拿复用包改

从零自研（不建议）

  • 我们从立项到今天走了 4 个月、25 次版本迭代
  • 我一路踩过 38 个记录在案的坑：反爬、采集管道断供、时间格式污染、模型下架……
  • 每个坑的修复都已沉淀在复用包里，重走一遍没有价值

拿复用包改（推荐）

  • 109 个文件的完整系统 + 6 份手册（搭建史 / 部署 / 运维 / 定制 / 采集后端 / 方法论）+ 我们的参考实现
  • 空库启动自动建表；自带 65 项自动化自检（相当于出厂检测，含义见下方改造第 6 步），交付时全绿
  • 照包内 FILLING-GUIDE 填空即可，验收标准明确：全局搜 {{ 清零
  • 包内另附给 AI 助手的接手说明——你们用 AI 工具改造时，AI 能直接读懂这套系统的红线

改造六步（从解压到能用）

  1. 先把空门户跑起来（第一天，约 10 分钟）：解压 → 装依赖 → 启动 → 浏览器打开。能看到空门户，说明环境没问题。这一步什么都不用填
  2. 填公司画像：先写中文版（给人看、以后也靠它维护），再对照翻成英文版（AI 实际读的），两份内容要一致。这是最重要的一步——写清楚医院板块是谁、有哪些业务线、同行有哪几家、什么不归我们管
  3. 换掉监控词表和同行名单：四类词逐条换成你们自己的（院区名 + 纠纷/投诉/曝光这类组合、科室和服务线、同行医院、卫健和医保的政策词）。⚠️ 中文平台上别放英文品牌词——我试过，一条声量都没有，搜回来全是不相干的
  4. 把 API 账号填进去：申请到的 key 填进配置文件（包里有逐项说明的模板）；再给门户设一个你们自己的邀请码
  5. 一路一路开跑：先跑竞品官网（最稳，当天就能看到内容）→ 再跑公众号 → 最后弄小红书（前提是先拿到那个浏览器工具的商用授权，见下面红线）
  6. 验收：跑一条自检命令（npm test）——包里自带 65 个自动检查点，专门盯时间格式转换、AI 返回结果的解析、模型出故障时能不能自动换一家这些以前真出过事的地方，相当于出厂检测，全绿就说明没改坏。再加两条：全局搜 {{ 一个不剩、门户从"空的"变成"有内容"。到这一步，系统就是医院板块自己的了
🚫 两条红线，动手之前先记住：
① Prompt 文件里的 {{COMPANY_CONTEXT}} 和 {{TAG_CANDIDATES}} 不是要填的空——这两个是程序运行时自动替换的变量，手动填掉系统直接坏。填空只照 FILLING-GUIDE 上的清单来，别看见 {{ 就填。
② 小红书那一路要用的浏览器工具 agent-browser-runtime↗ 不在包里：它是别人的开源项目，用的是 PolyForm Noncommercial 许可，公司要商用，得先联系作者拿授权。这件事排在最前面去办——授权没下来之前，其他几路照跑，不受影响。

多人怎么分工

📌 先说一条技术上的限制：同一时间只能有一个人跑采集（数据库同时只允许一个人写，两个人一起采会把彼此的数据覆盖掉）。所以分工的重点不是"大家一起采"，而是把复核、研判、校准、日报这些人做的环节分给不同的人。我们这套目前是我一个人在维护，这些活全压在同一个人身上，采集频率和校准速度都上不去——分工是我自己没条件做、但确实值得做的部分，供你们参考。
岗位人数每天花多久做什么
值班采集每天 1 人，轮流10–20 分钟启动当天的采集；小红书登录失效时扫码；看一眼开工自检的结果——哪一路超过 7 天没抓到新东西会标黄，看到就要查
版块复核每人认领 1–2 个平台或部门版块5–10 分钟看一遍自己那块、点赞或点踩、发现判错了随手记一笔——这些记录就是下一轮校准的原料
研判值守当天 2 人有事才做复核高危研判卡（出卡的人和复核的人不能是同一个）、定级别、按预案上报
日报汇总每天 1 人，轮流15 分钟把当天要点整理成早报发群：摘要 / 重要事件 / 风险提醒 / 建议动作
系统负责人固定 1 人每周半天收问卷、把答复写回判定标准、增删监控词、排班

这套分工不是我自己编的：舆情行业常见的是「报道组 + 分析组」两组制，或者「监测岗 / 研判岗 / 联络岗」三岗值班制，政府的预案里常见每天 9:00、12:00、19:00 各巡查一次——医院板块还可以再按院区分一层（研判岗一人认领一个院区）。出处见第 ④ 章末尾的来源表。

如果想多采一些：小红书可以多个账号轮流用，每个账号每天有各自的安全额度，人多就能多采。但采集的原则不变：量小、模仿真人的节奏、一有异常就退（连着两个词都抓不到内容，系统会自动停下来等人处理），不跟平台硬碰。

我踩过的坑（每一条都交过学费）

1故障会装成正常的样子

公众号那一路断了 37 天我都没发现——搜索接口被限速之后，日志上天天写着"搜索完成，0 篇"，看起来就像最近没有新文章。

学到的：监控系统自己也需要被监控。现在开工自检里加了一条"哪一路超过 7 天没进新内容就标黄"，就是这次的学费换来的。

2宁可空着，也不瞎编

抓不到发布时间就留空、标成"采集日期"，绝不拿抓取时间冒充发帖时间。

这类系统靠的就是可信：有一次被同事发现"2018 年的老文章显示成 3 小时前"，信任一下就没了。

3品牌词每轮都要搜

有一条骂自家品牌的帖子，因为词表在轮着搜，53 天都没被搜到。后来把品牌词单独拎出来，不跟着大词表排队，每轮都查。

对医院尤其要紧——「医院品牌名 避雷 / 投诉 / 纠纷」这类组合就属于必查词，一轮都不能落。

4时间格式一次弄对

"5小时前""昨天22:17"这种页面上显示的文字直接存进库，结果排序、显示、筛选三个地方全乱，回头修了 834 条数据。

复用包里已经修好了。提这一条是想说：数据存进库时的规矩，比多做一个功能重要。

5当天的事当天判完

小红书的帖子链接过几天就失效——高危帖必须当天就把研判做完，隔夜链接一死，只能重新采一遍。

所以值班安排上，"研判要和采集在同一时段做完"是硬规矩，不是建议。

6写进去不等于生效

判定规则在 Prompt 里改完了，模型不一定真照着做——我拿 6 条真实帖子、正反两个方向都试过，才敢上线。

每次改完判定标准，找几条已知答案的帖子喂给系统对一下答案，是成本最低的质检办法。

④实时预警：往哪个方向走

实时预警也是我们下一步想做的方向。这一章是另外补做的调研，不是我们已经跑起来的东西——先给一个能直接上手的做法，其余材料收在下面的折叠里，需要时再展开。

自己做"接近实时"：把词分成三档

思路不是把所有词都跑得更快，而是把最要紧的那批词跑得更勤。这跟我们现在跑的"品牌哨兵"是一个路子，行业里公开的做法也一样（核心词高频跑 + 其余词定时轮着跑 来源↗）：

🛡️第一档 · 每 15–30 分钟一轮

品牌词配上负面词，大约 20–50 个组合：「医院品牌名 医闹 / 纠纷 / 投诉 / 曝光 / 维权」，各院区名也配一套同样的。

每轮只取最新的 20–30 条，一天的请求量压在平台的安全范围内。

📋第二档 · 每 2–4 小时一轮

服务线、科室、医生名字、产品名——重要，但不是火烧眉毛的那类。

大概几小时能发现，跟得上日常运营的节奏。

🌐第三档 · 每天轮一遍

同行医院、行业和政策类的词——属于背景信息，慢一点没关系。

② 医疗健康信息属于敏感个人信息（第 28 条），处理它需要本人"单独同意"（第 29 条）。所以系统设计上有一条红线：库里只存链接、正文摘要、平台上公开的昵称，绝不把"能认出是谁"和"病情、就诊记录"这两样关联着存进去——一旦关联，性质就从"处理已公开的信息"变成"处理敏感个人信息"，合规要求完全不是一个量级

③ 合规审计办法里已经点名，"超出合理范围去收集、留存、加工已经公开的个人信息"是重点关注项 审计办法↗。截图这类证据要单独存放、限制能看的人、设一个保留期限

三条路线，投入从低到高，可以分步走

一花钱最少 · 1–2 周

把词分档跑 + 群机器人直接推：最要紧那档词 30 分钟跑一轮，黄级和蓝级由飞书机器人推群。

这样大概 30–45 分钟能发现——已经赶得上"黄金 4 小时"，甚至民营医疗同行说的"最好 2 小时内响应"也来得及。要注意控制风险：小红书那边一天的请求量压在几百次，间隔要随机。民营医疗响应窗口↗

二中等投入 · 1–2 个月

把分级规则写进系统 + 排三岗值班 + 红级卡人工：四色标准落到代码里，值班表落到具体的人。

这一档主要难在人力组织——一个人维护是做不了 7×24 值守的，人手够的团队更有条件把值班制立起来。合规的存储方案（只存链接和摘要）同步做掉。

三投入较大 · 按季度算

自建的部分 + 买一套商用工具补盲区：自建负责细到院区、科室的归因（这个商用工具做不了），商用工具负责覆盖面和突发发现。

配套出一份院级的《舆情管理制度》：分级、上报时限、谁负责、怎么处置。医疗版的时限一般是：紧急事件 15 分钟上报、1 小时启动处置、24 小时内首次对外发声。时限来源↗

⚠️ 有一件事不建议追：对小红书做"秒级、分钟级"的全流程预警。商用厂商自己在小红书上也做不到，投入产出比很差。把力气花在"发现之后 15 分钟内完成人工定级、启动响应"上，比把发现时间从 30 分钟压到 5 分钟划算得多。
