①两个灵感：不是让 AI 替人干活，是让它把准备工作做完

这两条来自一位从 MBB 出来做 AI 咨询的从业者的公开分享（他按「对企业回报从小到大」排了四类最常做的项目，本期先收两类）。外部视角 我们没有验证过其中的省钱幅度，放进来是当选题线索用，所以下面只讲机制，不讲「省了多少」。

#4销售电话打完，CRM 自己更新
痛点：电话打完，客户说了什么、卡在哪、下一步干嘛，全留在销售脑子里。CRM 周五才想起来补，follow-up 晚三天，客户已经凉了。
做法：录音 → 转文字 → 模型抽出下一步动作、客户顾虑、报价与交期 → 自动更新 CRM，顺手把跟进邮件草稿和待办建好。销售只需要读一遍点发送。
值钱在观感：客户当天收到一封细节齐全的跟进邮件，销售的专业度直接上一档。
#3客服工单自动分流，拿不准就立刻转人
痛点：60%–80% 的询问大同小异 ——「订单到哪了」「能改收货地址吗」「发票怎么开」。
做法：自动读完每张工单，有把握的用自己的知识库和订单数据直接答；没把握的把问题摘要加一版建议回复交给人判断。
命门不在回答，在 escalation：没有「拿不准就交人」这个机制，AI 一定会非常自信地说错话，而且那股「AI 味」会第一时间引起客户反感 —— 说错话和说得像机器人，是两个独立的差评来源。
两条的公约数：都是让 AI 把人干活前的准备工作做完，最后一步留给人点确认。这个形态既拿到了效率，又不用把对外责任交给模型 —— 我们内部推 agent 可以照这个模子。客服那条和客服团队正在做的方向是同一条路，可以直接拿去对照。

②先判一件事：这活该不该上 agent

Anthropic 官方的分法很直接：workflow 是写死的步骤，agent 是让模型自己决定下一步。能画出固定步骤的就是 workflow，别上 agent —— 这一步本身就是省钱。

WORKFLOW · 写死的步骤

  • 输入 → 固定几步 → 输出，每次走法一样
  • 可预测、可测试、便宜
  • 官方原话：对多数应用，「把单次调用配上检索和示例就够了」

AGENT · 模型自己决定下一步

  • 每次走法可能不一样，模型现场规划
  • 灵活，但「拿延迟和成本换任务表现」
  • 只在「需要模型自主决策、且要规模化」时才值
灵感对应的官方模式为什么不是 agent
销售电话 → CRMPrompt Chaining
串行，每步之间设 gate 校验中间结果		步骤固定：转写 → 抽取 → 更新 → 写草稿。没有「模型自己决定下一步」的必要
客服工单分流Routing
先分类，再送到对应的专门分支		分类边界是业务定的，不是模型现场发明的

一手 出处：Anthropic《Building effective agents》。五种官方 workflow 模式 = Prompt Chaining / Routing / Parallelization / Orchestrator-Workers / Evaluator-Optimizer，我们这两条只用到前两种。

③五步框架：每步都有出处

顺序不能乱 —— 前一步的输出是后一步的输入。第 2、3、4 步是「安全」的三道闸，第 5 步决定能不能规模化。

  1. 把流程画成固定步骤。拿纸画一遍：输入是什么、中间几步、每步的输出交给谁。画得出来 = workflow，照上面的表挑模式；画不出来才考虑 agent。
  2. 给每个动作按风险打分。OpenAI 的做法：按只读 / 写入、可不可撤销、要什么权限、有没有钱的影响四个维度打 low / medium / high，然后用这个分数决定哪些动作要停下来等人。
  3. 校验放在真正会出事的那一步旁边。官方原话「place validation next to the tool that creates the side effect」—— 不要只在最外层做一道总检查。这解释了「销售读一遍点发送」为什么对：卡点必须在发送，不在转写。转写错了能改，发出去改不回来。
  4. 先定升级机制，再谈回答能力。两个触发器：① 重试次数超阈值（几轮没搞懂客户意图就转人）；② 动作本身高风险（取消订单、批大额退款、付款）。阈值先保守后放开。实现上有个好形态：要人批的地方不是失败退出，而是挂起 —— 记一个审批中断加一份可恢复的状态，人批完从原地接着跑。
  5. 产出要能被机器自动校验。对得上系统数据、对得上条款原文、对得上溯源链接 —— 配得上自动校验的才敢规模化；配不上的，规模化多少就得人工复核多少。

第 2 步落到我们两个用例长什么样

动作风险怎么处置
读订单状态 / 保单状态低直接跑
更新 CRM 字段、建待办中（可撤销）自动跑，留日志
给客户发邮件、发报价与交期高（不可撤销、对外）必须停下来等人点确认

第 5 步落到我们两个用例的校验项

报价与交期要对得上系统里的真实值；工单回复引用的政策要对得上条款原文；写进 CRM 的字段要能反查到通话录音的哪一段。这三条配不上自动校验的，就别急着放量。

一手 第 2、4 步出处：OpenAI《A practical guide to building agents》；第 3 步出处：OpenAI《Guardrails and human review》。第 5 步与本期《AI 圈周报》第 11 期「选型必问」同源。

作者自己报的失败模式：客户的表达方式会歪掉判断。把小事说得很严重的会被误升级，把严重问题说得很平淡的会被漏掉。所以第 4 步要补一条 —— 升级判据不能只看客户措辞，必须把客观字段（订单 / 保单状态、时效、金额）一起喂进去。

⑤从哪学：两条路，先看自己写不写代码

工具口径先说清。集团同事手上只有三件工具：Cherry Studio / Claude Code VSCode / CC Desktop，没有任何订阅，全走令牌网关按量计费。所以这份清单不列 Zapier、n8n、Make 这类需要独立订阅的平台 —— 网上大部分「自动化教程」讲的正是那些，看了也用不上。

⑥合规两条：动手之前过一遍

一、通话录音转写涉及客户个人信息，必须有明确授权再做，走法务。口头同意不算。
二、抽出来要发给客户的内容（报价、交期、工单回复）不能让模型直接发出去，必须停在「人读一遍点发送」这一步。这不只是合规要求，也是第 3 步那条设计原则本身。

⑦本周作业

看完这一页，你手上这个流程该做的三件事
  • 把你想自动化的那个流程画成固定步骤（第 1 步）。画不出来，先别动手。
  • 给每一步打风险分，圈出那个必须留给人点确认的动作（第 2、3 步）。没圈出来，说明你还没想清楚它会在哪出事。
  • 路线 A 的同事：装好 skill-creator，拿你圈完的那个流程跑一遍，把用了多久记下来——我们需要一个本地实测数替掉官方那个「15–30 分钟」。
