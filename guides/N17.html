CHAPTER 00 · 先搞清楚你在玩什么游戏

规则不是一套，是两套——而且互相矛盾

这一章不搞懂，后面所有技巧都会用错地方。

💡 怎么判断自己在哪一套里？
看三件事：① 谁办的——学校社团 + MLH 背书 = 校园赛；厂商冠名 = 厂商赛。② 有没有公布权重——公布了百分比的基本都是厂商赛。③ 交付形态——展位巡场（science fair）多为校园赛；线上提交 + 视频 + Devpost 页面多为厂商赛。
国内的"小红书黑客松巅峰赛""AdventureX""美团 AI 黑客松"等，评分导向更接近厂商赛（看落地、看影响、看路演）。

⏳评审的"物理约束"——最被参赛者忽略的一层

官方指南 这一节解释了为什么所有 demo 技巧都长成那个样子。

约束数字对你的含义
MLH 现场评审每队 3 分钟；评委预算 4 分钟/项目（2 分钟展示+demo、1 分钟提问与计分、1 分钟走路）你要能重复讲三遍且每遍一样稳（MLH 建议每项目 3 位评委看）
MLH 决赛机制Stack Ranking（名次制）不是加总分——每位评委只报自己那组的 top 3，记 3/2/1 分"平均分不错"没用，必须进某位评委的前三
Gavel（HackMIT）"平均每位评委只看了全场 5% 的项目"；机制是两两对比你不是跟全场比，是跟随机配对的少数几个比——目标是在一次正面对撞里赢

💡 Gavel 为什么不打绝对分？
作者 Anish Athalye 的论点："人在做比较判断时，比在确定绝对分数时准确得多。"而且绝对打分有顺序依赖问题——"评审结果会依赖于作品被评审的顺序"。所以他改成两两对比 + Crowd-BT 算法排序。
这条和下面那位评委说的"评委是在跟刚看过的 6 个排序"是同一件事的两个证据——一个来自算法设计者，一个来自现役评委。
🧠评委不是在给你打绝对分，是在跟刚看过的项目排序

多源印证

"Judges are not evaluating your project against an ideal. They are ranking it against the six they just saw while trying to remember which one had the map."
— dev.to 作者 kurbaitaev，2026 年 7 月十天内连判三场，2026-07-27

由此推出一条极其实用的准则：

"Pick the sentence you want a judge to repeat to another judge an hour later. Build the demo that earns that sentence. Cut everything that does not."
（挑一句你希望评委一小时后转述给另一个评委的话，照着这句话做 demo，其余全砍）

⚠️ 反向意见：Devpost 评委 Richard Moot（Square）说他刻意反着来——"我鼓励评委尽力按个体评估，因为很容易变成拿项目互相比较。"说明这是评委自己也在对抗的偏差，但偏差确实存在。

CHAPTER 01 · 你的第一个问题

怎么构思项目：选题是唯一一件 AI 替不了你的事

失败案例的共同根因几乎都在这一步，而不在开发。
📋动作 1：先读评分表，再读赛题

多源印证

"The rubric tells you what gets rewarded, while the problem statement only tells you what to build, and most teams confuse the two."
— AngelHack（办过 450+ 场赛事的主办方），2026-06-08
"Read the rules before. Don't start writing anything before you really understand the problem space, the objectives of the hackathon, and what the judges are probably looking out for."
— Jan-Niklas Wortmann（JetBrains DevRel，评委），2026-06

具体怎么用：评分表里"创新性占 30%"→ 奖励对简单问题的巧妙切角；"Technical Execution 占 50%"→ 你得留出时间写 README 和架构图。没公布评分表就直接找主办方要。而且赢家是在每次重大取舍前重读一遍，不是开头看一次。

中文侧完全对上——《第一次参加黑客松，我们差点输在团队协作》复盘的第一个坑就是：

"没先按照评分标准统一目标。大家一开始都在讨论要做什么，却没有先想清楚评委到底看什么，导致后面做了不少和评分关系不大的工作。"

⚠️ 还有一条很反常识的官方数据——Karen Bajza-Terlouw（Databricks 评委）："我做的第一件事是过一遍黑客松要求的各项条件。作为评委，看到有那么多提交连基本要求都没满足，这挺让人吃惊的。"

🎯动作 2：从"你自己被烦到的事"起手，不从"最酷的新工具"起手

多源印证

"不要 start with '什么是最酷的新工具'，而要 start with '有什么是我现在能做、而以前做不了的'。"
— Bonnie Xu（OpenAI，JetBrains 黑客松评委），2026-06（中译）

💡 这组案例真正的可复用之处：三个判断标准

① 专家瓶颈 —— 这个领域是否因为专家不够而产生系统性延迟？（许可审批、医疗诊后、道路检查）

③ 信息不对称 —— 是否存在一方有知识/权力优势、另一方被动接受？（医生 vs 患者、企业 vs 消费者）

  • 任务切换的代价——"人的大脑并不是一台可以瞬间切换任务的计算机。当我从黑客松的复杂算法逻辑中抽身，去回复学员关于'环境配置'的基础问题时，大脑需要经历一个痛苦的'降噪'过程。这种切换不仅流失了时间，更损耗了心智带宽。"
  • 知识的诅咒——"当我掌握了某项技能后，我就会下意识地认为这件事很简单……这些我眼里的'常识'，其实非常消耗执行时间。当几十个这样的'微小细节'叠加在一起，工作量就像滚雪球一样压了过来。"

  • ② 任务分三级——体力活（不动脑、纯手速，放在精力涣散的下午）/ 脑力活（路径清晰但要专注，需整块时间）/ 高风险项（容易出 Bug、如尝试新框架，最容易导致节奏失控）
  • ③ 冗余设计——"以前我习惯把计划排得严丝合缝，觉得这样才叫'高效'。现在我明白，真正的效率是承认摩擦力的存在。如果我预估一个技术调研需要 2 小时，我会直接在日历上划掉 3 小时。"
"逻辑上的'稳'，决定了你能走多远；而执行上的'节奏感'，决定了你能走多久。
如果你总是在熬夜救火、总是在最后一刻心惊胆战地交付，那么哪怕你逻辑再强，你也是在刀尖上跳舞。"

🧩能直接套的 4 句话框架

评委 来自一位 ex-VC 投资人、AdventureX 评委，一天看完 30 多个项目后写的：

🎤 4 句话 Pitch 框架（以某赛道 TOP1"AI 健身教练姿态辅助系统"为例重写）

  • 1️⃣ 我们看到的痛点是…… → 用户想要 1v1 的健身指导。
  • 2️⃣ 常规的解决方法是…… → 找私教，但支付不起昂贵费用，也不见得能找到足够专业的。
  • 3️⃣ 我们的解决方法是…… → 通过 AI + 智能硬件判断发力姿势是否标准，让每个用户都能普惠地享受私教指导。
  • 4️⃣ 我们做出这个方案的难点是…… → 需要用视觉算法、机电信号等识别姿势。
— 小红书《3分钟黑客松pitch｜像十年老founder讲清项目》。作者注：这套框架也适用于面试、商务谈判、卖货，甚至项目启动前的战略梳理。真投资 pitch 还要加：痛点市场规模 + 盈利天花板。

这条建议的分量在于它的观察前提——"在最后五进一的关键 pitch 上，我周围好几个评委在一开始都没有听懂。"连进了决赛五强的项目，评委都可能听不懂开场。

⏱️90 秒内必须看到东西在跑

评委

"You have to be able to show something working within about 90 seconds."
— Jono Bacon（Stateshift CEO，JetBrains 黑客松评委），2026-06

整篇的定调更狠："A strong project with a confusing demo loses to a simpler project that the judges understand."（一个强项目配一个让人困惑的 demo，输给一个评委能听懂的简单项目）

赞助商赛道负责人给的 2–3 分钟分配：Hook 15 秒（自我介绍 + 问题 + 一个可代入的场景）→ Demo 60–90 秒（只走核心功能）→ Tech 30 秒（最难那个技术坎）。

⚔️ 争议 4（最关键的一组）：开场第一句先讲问题，还是先讲"这是什么"？
A 派：先讲问题，让评委先"疼"
"先说你要解决的是什么问题。你需要让评委和你共享对这个问题的愤怒。"（Jono Bacon，评委）
Avi Press 补一句："大家总是跳过这步。"

"大多数队伍把约 5% 的 demo 时间花在问题上、95% 花在方案上，然后对自己的'影响力'得分很低感到意外。赢家的配比更接近 30% 问题 / 70% 方案。"（AngelHack）

中文侧同向："讲故事，别上来就说用了什么架构什么模型，先讲一个场景'你有没有遇到过这种情况……'让评委先共情再引出方案。"
B 派：先给锚点，故事后置（2026-07 现役评委）
"得分高的队伍开场是一句朴素的陈述：这是一个为 Y 做 X 的工具。失分的队伍开场是铺垫——市场规模、个人故事、一个花了四十秒才讲到产品的问题陈述。等产品终于出现时，我已经花掉三分之一的时间却还不知道自己在看什么。"

"评委不是对你的故事有敌意。他们只是在没有锚点的情况下记不住它。先给锚点，故事才有地方安放。"— dev.to/kurbaitaev，2026-07-27
两派其实都在反对同一件事：40 秒还没说到产品。可行的合流写法——第 1 句给一句话锚点（为 Y 做 X 的工具）→ 第 2–4 句给具体到某个人的问题场景 → 立刻进 demo。这样既满足 B 派的"先锚点"，又保住 A 派要的 30% 问题时长。
上面帝国理工那个案例正好是完美示范："AI 系统最大的问题不是不聪明，而是会瞎紧张——84.6% 的误报率，让整个行业都在做无用功。"一句话里同时给了锚点、问题和数字。
🎬先写 demo 脚本，再写正经代码

多源印证（四方独立同构）

"如果你在开始写代码前写不出这个脚本，说明你还不知道自己要做什么……花两小时写脚本，通常能省下六小时去做那些根本不会出现在最终 demo 里的功能。"
— AngelHack。五要素：① 一句话问题（绑定一个具体的人，不是一个人群）② before state（今天这人怎么绕过去、代价多少）③ trigger（demo 从哪个动作开始，让评委知道该看哪）④ "aha" moment（唯一一个要评委记住的瞬间）⑤ close（一句话把 demo 接到规模/影响上）
"从 demo 开始，然后倒着建。我们前两小时在勾勒到底要给评委看什么、用什么输入、输出长什么样、'wow' 的瞬间在哪。每一个架构决策都过一遍'这会让 demo 更好吗'。"
— MIT LLM Hackathon for Chemistry and Materials 一等奖，2025-09-25
"先在提交表里写 elevator pitch 和 project story——这几乎就是你的 demo 视频脚本，而且是在你写第一行代码之前就完成的。"
— shemmarie（25 场参赛），Devpost 官方博客
"没提前写 Demo Story，功能越堆越多，却串不成一个让人记住的场景。" → "🔹开发前先写完整 Demo Story，再反推必须做的功能"
— 小红书《熬到凌晨2点》（从失败方向印证）

⚔️ 争议 5：mock 到什么程度？
尽量 mock
"能 mock 的全 mock，确保所有表单都已填好、和用户的来回流程顺畅。"— Colin Lowenberg（Nebius，评委），2026-06
核心绝不能 mock
"不要 mock 任何核心的东西，评委通常看得出来什么是 mock 的，而且会扣分。数据源和第三方 API 需要的话可以 mock，但绝不要 mock 评委专门来看的那个功能。"— AngelHack

🎙️台上的具体动作

单点，但都是可当场执行的

  • 开场加个梗。"让评委笑出来 = 印象深刻。别平平淡淡开场。"
  • 超时了也要把话说完。"有人一超时就自动停，大错特错！正确做法：继续说，把核心价值点重述一遍。"
  • 结尾疯狂点题。"最后一定要说队伍号码和名称！如果涉及投票，再次强调你解决的问题价值。"
  • 做对比。"'现在大家都是这样做的，但我们可以这样做'，一对比价值感立刻出来。"
  • 讲清楚"这件事很难"。"技术在路演中占比很小，但关键是：如何让评委知道'这件事很难解决'？不是秀代码，是讲清楚技术壁垒。"
  • elevator pitch 是最重要的 30 秒。"评委在你开口的前半分钟就已经形成了判断。"
  • 只排练开场 30 秒。"大声排练开场三十秒。不是整场 demo，是开场。分数是在那里定下来的。"（评委）

⚔️ 争议 6：被问到没做完的功能，该硬扛还是该交底？
硬扛派
"绝对不要被问倒……被问到不会的？别说'这个我没想过'，换成'这是个很好的方向，我们下一步正好计划……'"— 小红书《黑客松演示环节怎么办？》

John Kim：把没做的功能框成设计决策而不是缺口——"我们有意把它砍掉以聚焦核心体验"，听起来远好过"我们时间不够了"。
交底派（评委实证）
"对什么能用、什么不能用、怎么实现的，要非常直接。评委看得出你在绕着一个还不存在的功能说话。坦诚反而读起来像自信。"— Avi Press（Scarf 创始人 CEO，评委）

要，而且是决胜点

检测结果："主观行为政策 + 无条件 IP 许可 = 他们无限期保留你的作品。"
— 该发现所依据的论文已提交 CHI 2026 会议。转述自公众号《黑客松获奖案例：发现2026年AI创业的六大范式》（碳硅边界，2026-02-24）
⚠️ 报名前值得花 10 分钟确认的三件事
① IP 归属——赛事条款里有没有"无条件许可"（unconditional license）？你的作品赛后还能不能自己商业化？
② 行为条款的主观性——"主观行为政策"意味着主办方可以单方面判定并据此处理你的作品。
③ 保留期限——是"活动期间"还是"无限期"？
这三条对打算把黑客松作品继续做成产品的人尤其关键——第 7 章里"值得参加的六条判据"其中一条就是"结束之后有真实下文"，而条款直接决定了你有没有"下文"的权利。

⚠️ 诚实标注：这是单一来源的转述，我没有拿到该黑客松条款原文逐条核对，也没有验证"无限期保留"这一判定是否成立。请当作"该去核对条款"的提醒，而不是对某场赛事的结论。不同赛事条款差别很大，MLH 体系就明确要求作品赛后保持公开、归作者所有。

— 小红书《港大Jennie｜AI黑客松备赛分享》

🔒技术栈用最熟的，绝不现学

多源印证

  • "不要拿新语言或新 web 框架做实验，那只会拖慢你……这不是尝试'本月最佳 JavaScript 框架'的时间和场合。"（Nick Singh）
  • "用你已经熟悉的工具，和你已经熟悉的人一起工作。"（Jan-Niklas Wortmann / JetBrains 评委）
  • "如果你必须用某个特殊的库，赛前就去试。你绝不想在比赛中途才发现这个库的文档很烂。"（Reddit r/hackathon）

CHAPTER 05 · 2025–2026 新变量

AI 时代特有的坑：技术平权之后，比什么？

这一章是本次调研里信号最新的部分。
2026 年最大的规则变化：评委开始用 AI 逐行核对"你说的"和"你交的"。吹牛成本第一次被量化了。
🔬Devfolio 的 AI 审计层：claim ↔ code 对账

平台官方 Devfolio 做的不是"AI 评委"，而是 evidence layer——agent 用 read/grep/ls 走一遍仓库，逐条核对 pitch 里的 claim 与代码是否对得上，产出带 file:line 引用的审计。

"It can notice that a team claimed a custom model and shipped a wrapper. It can notice that a README describes a backend the repo does not contain."

实际扣分记录："Reduced Technical Execution from 8 → 5. The submission claims 'multi-tenant isolation with row-level security,' but db/policies.sql only checks that a user is authenticated."

另一例："docked Originality from 7→4"，因为 src/model.ts:42 显示所谓"自研架构"其实是 transformers.AutoModel.from_pretrained('bert-base-uncased')。
— Swarnim Walavalkar，《The Discerning Machine》，Devfolio Blog，2026-05-18

同文里对参赛者最有杀伤力的一句：

"A polished README becomes a longer list of claims to check. A blank README has less to disprove."
（精美的 README 只是变成一张更长的待核对清单；空白 README 反而没什么可被证伪的）
💡 这条的可执行含义
不是"少写 README"——README 在多数赛制里是加分项。是"写的每一句技术宣称，都要能在仓库里指到具体文件"。
实操：提交前把 pitch 和 README 逐句过一遍，指不到文件的那句直接删掉。少吹一点、句句可查，比吹满被砍分划算。

同源的另外两个观察：出现了 "feature stuffing"（AI 让堆功能变廉价，于是大家堆功能）；以及评委反馈"现在所有项目的设计看起来都一样"——建议参赛者把 AI 省下来的时间投到设计质量上。

⚖️技术平权之后，赢家给的答案：故事 + 审美

单点，但是一等奖的第一人称

"所有人都在用 AI 写代码。技术门槛被拉平了。48 小时，每个队都能极速产出 demo。那评委在看什么？你在讲什么故事。你的产品完不完整。"

"故事是最难的。因为技术平权了，demo 谁都能出——但'这个东西到底在解决谁的什么问题'，这个问题 AI 回答不了，只有你能回答。"

"AI 让你更快地产出了，但如果没有审美，你只是更快地产出没有审美的东西。"

"在写第一行代码之前，我先回答了一个问题：'用户看到这个产品，会联想到什么？'……如果要问为什么我们能得一等奖，一定要分享一个点：先定调，再动手。"
— 小红书《黑客松拿了一等奖，不是因为我代码写得最好》

评委侧的独立呼应："AI 把'做出来'这件事变得更容易，但分水岭更清晰了……当'能做出来'不再稀缺，大家会更快被拉回到基本问题：你到底在解决什么真实需求？最小闭环能不能成立？"

🎮一份完整的 AI 黑客松工作流实录（得奖，游戏方向）

单点，但过程颗粒度最细 这是本次调研里唯一一份把"AI 到底帮了什么、哪里必须靠人"拆到工序级的复盘：

  • 赛前一周先试工具，不直接写。试了 Pencil（偏设计工具，非素材流水线）、MuleRun（偏 agent 托管），最后选定 Claude-Code-Game-Studios——"它最有价值的地方不是自动生成游戏，而是把 Claude Code 的工作方式组织成一个更像游戏工作室的流程：多个专职 agent、成套工作流和规则、强调文档分工校验"
  • 先用 ChatGPT 把需求收敛成文档，再交给编码。"这一步很重要，因为 AI 编码最怕需求模糊。文档越清楚，返工越少。"
  • 真正编码时间不到 4 小时——"最花时间的其实不是写代码，而是把需求讲清楚"
  • 赛题"你只能做一件事"反而帮他做了减法：玩家只负责移动、技能自动化、AI 参与叙事和决策。"操作复杂度一下就降下来了，同时 AI 的存在也不再是噱头"

AI 的能力边界，他给了两条很具体的判断：

"AI 很擅长先把'能跑的东西'搭出来，但比赛里真正拉开差距的，还是画面、反馈和节奏。"

"AI 更擅长生成大画面，不太擅长生成小而清晰、可直接拿来做角色头像的平面图标。"

"AI 可以很快给你一个 60 分版本，但从 60 分到 80 分，还是要靠非常具体的反馈和反复调优。"
— 公众号《一次 AI 游戏黑客松复盘：从灵感、踩坑到最终得奖》（狮子的牙齿，2026-03-31）

最后的技术组合与一句总结：Claude Code 主力编码 / ChatGPT 整理需求 / Gemini 音效与视觉素材 / PS 手动做遮罩切图。

"AI 做游戏已经不是'能不能做'的问题，而是'你会不会组织它'的问题。"
"对我来说，这次不是'AI 替我做游戏'，而是'我学会了怎么组织 AI 做游戏'。"
🪤失败方的诚实复盘：难的不是写代码，是"结构化"和"审美标准"

反向单点 一位数据分析师，公司内部赛 200+ 队进 45 强、没进 15 强决赛。她指出的卡点比获奖帖更有信息量：

"很多人觉得现在用 AI 写代码、画原型、生成视频都不难，确实如此。但真正的难点在于'结构化'和'审美标准'（taste）。"

"当我试图将美发师复杂的营销逻辑（比如 Before/After 的完美对比）提炼成 Agent 能够稳定执行的标准化流程时，我卡壳了。短时间内，在一个自己不熟悉的非标行业里，把'美感'和'网感'变成结构化的代码逻辑，真的太难了。"

"虽然我能总结出爆款的表面规律，但因为缺乏欧美发型师的真实体感，我很难深刻理解'用户为什么买单'。我只能看到表象。这恰恰证明了：真实的行业经验和对特定垂类场景的深度理解，依然是极高的护城河。"
— 公众号《AI黑客松比赛真实复盘：200支团队突围前45》（艾理Emily，2026-03-10）

她做对的一件事值得单独抄——选场景时的减法逻辑：面对众多海外中小商家场景，最终放弃餐饮、选美发，理由是三条可验证的判断：① 短时间内保证 MVP 效果必须只打透一个场景；② 美发行业利润率更好、商家更愿意付钱；③ 发型的 Before/After 视觉呈现在社媒上更容易出效果（= 可演示性强）。

👉 注意这和第 1 章那三个选题维度（需求强度 / 可演示性 / 赛道契合）是同一套东西，只是她用在了"选哪个行业"而不是"选哪个点子"上。

🎭"answer" vs "act"：2026 年的分水岭

观点，但表述最锋利

"There's a meaningful difference between a tool that answers and a tool that acts."
（一个"回答"的工具和一个"行动"的工具，有本质区别）— Claude Code Hackathon 指南，2026-04-20

配套的反模式清单：❌ 花哨界面 + "看它能干啥"式演示　❌ 单 prompt 工具（评委已经看腻）　❌ 野心大但做一半（"一个打磨好的可用 MVP 每一次都打败一个野心勃勃的半成品"）

✅ 正面判据：一句话答得出 "who is this for, and what does their day look like without it?"；具体到"这个工具帮工程师每周省 3 小时"；"最好的提交可以直接当 YC 申请用"。

官方规则印证 多个 2026 Claude 系黑客松的 Technical Execution 明确写：判断 Claude 是不是"让这个项目成立的核心，而不是加上去的"（core to what makes the project work rather than just added on）。

🤖AI 写的代码"看起来完美、跑起来没报错，但算的根本不是你要的东西"

多源印证

"AI 负责样板代码、集成胶水和 UI 脚手架。新颖的逻辑手写，因为评委会追问你代码里差异化的部分，如果你解释不了，他们会察觉到那个断层。调试 AI 代码有时比自己写还慢，这意味着瓶颈从生成转移到了验证。"
— AngelHack，2026-06

📐eval 已经从"加分项"变成"必答题"

主办方 AngelHack 2026 agent 黑客松 playbook 给出的标准五指标（组织方提供共享 eval harness，让队伍从 day 1 就对着它建）：

指标定义
Task completion rate测试场景中达成目标的百分比
Tool-use accuracyagent 是否在正确的步骤调用了正确的工具
Cost per run每个成功任务的 token 花费与 API 成本
Latency从 prompt 到完成的时间
Hallucination rate虚假陈述或编造工具调用的频率

获奖项目正在把"可验证性"做成卖点：

  • LORE（GitLab 2026 大奖）：8 个协同 agent + 知识图谱路由 + 43 个测试（黑客松项目里罕见的严谨）。评委 April Guo 原话："This feels like a product, not a hackathon project."
  • Sim Francisco（Anthropic Build Day 第二名）：1 万个基于人口普查的合成居民数字孪生；预测 2024 大选 81.3% vs 实际 83.8%——即"自带 eval 结果"
  • Tekton（第一名）：3D 重建唐代建筑，每个组件可溯源到历史出处；用独立 verifier 子 agent + 自纠错循环
  • Aegis（GitLab Runner Up）：每个决策都给可解释理由 + 已部署到 Google Cloud、production-ready
  • Klaviyo：每条建议带历史事故引用——"This matches incident 2025-06-28 where throttling to 15% resolved database timeouts within 20 minutes."
💡 共同模式（归纳）
赢的项目都在 demo 里露出了"可验证性"——测试数、溯源链、eval 对照、决策解释。这正好是"套壳"最难伪造的东西。
🔍评委会对你的核心主张做"对抗性实测"

评委 AI Slop Scan Hackathon（43 支队伍）评委、CNCF Kubestronaut、KubeCon 安全赛道程序委员：

"在程序委员会待久了你会很快学到：呈现质量和实质内容是两个独立变量。有些最差的投稿排版最漂亮，有些最好的看起来很糙。所以你不再读它的主张，而是开始测试它……我不问这个工具说不说自己能抓 slop，我问的是：我故意喂它 slop 的时候，它抓到了吗？"

结果：把一段 AI 生成的招聘启事喂给某检测工具，工具给了 100 和 91 分（判为真人写的）。检测准确率直接打 0 分。
— Myroslav Mishov 访谈，2026-06-26

他给的最高分给了一个主动换问题的队伍——不做"这是不是 AI 写的"（不可证伪），改做"这段文字是否显示出思考痕迹"（可测量）：

"A detector built on a verifiable question can be tested, debugged, and trusted. A detector built on an unfalsifiable one can only be believed."

👉 直接含义：如果你的项目核心主张是"我能识别/判断/检测某件事"，假设评委会当场拿一个刁钻样本喂给它。要么保证核心能力真的稳，要么把问题重新定义成可测量的版本。不要把不可证伪的主张写进 pitch 的第一句。

📄提交页：Devpost 官方模板 + 一个冠军的实际做法

官方 project story 标准结构：

## Inspiration → ## What it does → ## How we built it → ## Challenges we ran into → ## Accomplishments that we're proud of → ## What we learned → ## What's next → ## Built With（Built With 里赞助商工具必须打上标签）

EcoLafaek（AWS AI Agent Global Hackathon 冠军）在这个模板上多做的六件事，可直接抄：

✅ 冠军提交页做对了什么

  • 标题行下方立刻放 Live Demo + Documentation 两个链接——评委不用找
  • Inspiration 里放第三方权威数据——引用 JICA 调查"Dili 每天产生 300+ 吨垃圾、100+ 吨未被收运"。不是"我觉得这个问题很重要"，是可核查的数字
  • How we built it 直接嵌架构图 + 指向独立架构文档站
  • Challenges 写具体技术坑 + 解法（多轮 tool calling 顺序错乱 → 改 tool description schema、加系统提示、加对话历史）——这正是 AI 审计最难挑刺的写法
  • Accomplishments 用可验证运行数据：线上域名、50+ 条真实上报、3+ 活跃用户、25+ agent 交互。小标题就叫 "Production Deployment with Real Users"
  • 结尾加自定义章节 "Impact Metrics We're Tracking"（超出模板）

AWS 官方获奖评语的措辞值得反推："impressively leverages multi-modal reasoning and AgentCore to autonomously chain tools" + "effectively empowers the community to tackle the over 100 tons of daily uncollected waste"——即技术手法名词 + 量化影响，与其 50% Technical Execution / 20% Impact 的权重完全对应。

另一条来自 40 场参赛者：留至少 15% 的赛程做提交打磨；用 GIF + 内嵌图片 + Markdown 加粗关键词 抓评委注意力。

Takeaway —— 线上赛的提交页不是"交作业"，是你唯一的销售页面。三条硬约束记死：视频 ≤3 分钟（MLH ≤2 分钟）、YouTube 公开、留 15% 赛程做提交。三条软技巧：顶部放可点的 Live Demo、Inspiration 用可核查数字、Accomplishments 用真实运行数据。
CHAPTER 07 · 反向证据（最值钱的一章）

也有人参加完就祛魅了，理由值得看

小红书上获奖帖远多于失败帖，幸存者偏差严重。这一章专门放反面。
💢反向 1：AdventureX 现场差评（两篇独立，同一届）

反向

"①审核乱……我的申请一直卡在第一步（卡了大概两周），一直到正式开始前一天晚上十点钟才告知被拒绝。
②管理乱……有些小展台都不在主会场也没有提示。
③产品很无聊，是真的很无聊。单纯做 ai tool 卖 token 的公司得有十家，宣传不同黑客松的得有五家……很多公司要么硬件功能完全不闭合要么根本没带硬件来。
⑤是性压抑交友平台，是精英主义炫耀平台，是小红书博主探店平台……总体呈现一种自我狂欢且浮躁之感。"
— 小红书《AdventureX极其混乱。》102 条评论。作者置顶评论："真情实感的写的帖子已然是被工作人员攻击了"
"就算有 AI 编码工具加持，短短五天的开发周期里，参赛作品大多只是拼接现有接口……整场活动技术氛围很淡，反而充满浮躁的圈层狂欢。"
— 小红书《AdventureX 黑客松 太烂了！》53 条评论

⚠️ 平衡视角：该帖高赞回复是"任何事情都是循序渐进的……从九岁小朋友到初中生、高中生，大家都有自己的想法和执行能力，为所有人种下一颗创新创造的种子，我觉得这个意义就足够了。"

🧊反向 2："我已经祛魅了"——一篇很冷静的退出理由

反向

"大多数参赛选手是奔着创造的快感来的，享受'做出来'的成就感，至于这个东西能不能用、有没有人需要、能不能落地，并没有一个客观的评价。而且随着加入的人越来越多，想法高度同质重叠。"

"更让我冷下来的是对主办方和投资人的观察：主办方肯定是有目的的，但是表露的有多明显要看水平；投资人能不能言之有物，还是为了说而说，还有可能是带着自家项目来评分的。"

"黑客松可以去，但要先想清楚自己的目的。为了玩的快乐，值得去；为了找同频的人，有可能但靠运气；为了商业化落地，你需要非常刻意地筛选。"
— 小红书《黑客松可以，但我已经祛魅了》
😤反向 3："认真做了一个能落地的产品，反而没获奖"

反向 结果反直觉的样本，和第 1 章"要做能落地的"直接相左：

"我是文科生，黑客松刚开始只能做一些天马行空的 demo，拿了 7 个奖。我却一直心虚，因为知道落地性很低，所以一直想做一个真正能落地的产品。于是在某个更大的赛场，我和 2 位顶尖技术精英及 1 位设计精英组队，做了一个非常成熟、能直接落地、解决痛点的产品，可却没有任何奖。"
— 小红书《认真做了一个能落地的产品，反而没获奖》52 条评论

⚠️ 该帖后半段提出"黑客松是资本做局、故意捧不落地的 demo、然后抄袭能商业化的产品"的推测。这是作者的主观怀疑，没有证据支撑，本报告不采信为结论，但"落地性强反而落选"这个现象本身有记录价值——它和第 0 章两套规则、以及"赞助商要的是能展示他们技术的项目"是自洽的：能落地 ≠ 能展示赞助商的技术；在 MLH 体系里更是明说了"有没有用不重要"。

🧭所以：怎么挑一场值得去的黑客松？

单点，但这是本次调研里最实用的一份"选场子"清单

✅ 判断一场黑客松值不值得参加（六条判据）

  • ① 时间够紧。24–72 小时是甜点区间。"超过一周的'创业大赛'本质上是另一种东西——它在考你怎么写商业计划书，不是考你怎么跑出 demo。"
  • ② 最终交付物是可跑的 demo，不是 slides。"评委要不要在你的 laptop 上戳一下你做的东西，是这件事是不是黑客松的分水岭。"
  • ③ 评委是懂行的人。"如果评委是大学老师加政府代表加校友嘉宾，恭喜你，你参加的是创业课结课汇报。"
  • ④ 主题有真实约束，但不死板。"约束足够窄到逼你做选择，但又足够宽到容下不同的 taste。"
  • ⑤ 现场密度高。"24 小时不关门……半夜两点能找到人帮你 debug。"
  • ⑥ 结束之后有真实下文。"如果颁完奖大家就解散了、群也死了，那这场 hackathon 的价值就只活在那 48 小时里。"
— 小红书《一个真正值得参与的黑客松有什么特点？》。作者点名认可：AdventureX、EAZO、Tone Jam；明确排除："学校里挂着'创新创业'名字的大赛、地方政府办的'AI 大赛'、企业赞助的'创意马拉松'——大部分都不在这个名单里。"

⚠️ 注意这份清单把 AdventureX 列为"公认的好场子"，而反向 1 的两篇差评正是冲着 AdventureX 去的。同一场活动口碑两极——这本身就是信息：大场子的体验方差极大，取决于你是去做东西还是去看展。
官方侧的一条印证：MLH 建议评审用 science-fair 摊位式而非分房间制，理由是"分房间的队伍只跟同房间的项目比，经常很难做到公平"——组织质量确实会直接改变你的胜负。

Takeaway —— 去之前先回答一个问题："如果这场没有奖、没有排名、没有评委、没有奖金，只有一群人聚在一起做东西，我还去吗？"（出自小红书《黑客松没获奖怎么办？》）——这个问题的答案决定了你该按哪一章去准备，也决定了没拿奖那天你会不会难受。
CHAPTER 08 · 可直接照做

四张清单：赛前 / 赛中 / Demo 前 60 分钟 / 提交页

上面所有内容压缩成能打勾的动作。

📋 清单 A：报名之后、开赛之前

  • ☐ 判断你在哪一套规则里（MLH 校园赛 vs 厂商赛）——这决定后面所有取舍
  • ☐ 拿到评分表和权重（没公布就问主办方要）；按权重分配工时
  • ☐ 确认 Stage One 的 pass/fail 硬门槛：是否真用了指定 API、是否切题、要件是否齐（评委原话：大量提交连基本要求都没满足）
  • ☐ 搞清楚最终交付什么：视频时长上限、README 要求、提交截止、走桌 demo 还是台上路演、有没有 slides、pitch 几分钟
  • ☐ 查清赞助商名单和各自赛道奖；确认赞助商是否真的到你这场
  • ☐ 查评委是谁、什么背景
  • ☐ 搭好环境：boilerplate、部署流水线、账号权限、API key、sandbox 权限、一条端到端测过的 build pipeline
  • ☐ 写一份自己的能力模块清单（"报菜名"用）+ 四句话自我介绍
  • ☐ 技术栈锁定最熟的；要用的新库赛前先跑一遍
  • ☐ 想 2–3 个候选点子（点子可以提前想，代码不行）

📋 清单 B：开赛后

  • ☐ 第 1 小时：定唯一目标（赢 / 学 / 社交，只能选一个）；签团队协议（同步频率、分支规则、砍 scope 信号、任务四要素、关键岗位备份）
  • ☐ 前 2 小时：走遍赞助商展台，直接问"你们最想要什么 / 如果我做出来你们选我们吗"
  • ☐ 选题前：有争议的方向先做 30–60 分钟最小实验；三问过滤（需求真不真 / 几小时能不能做完 / 30 秒能不能讲懂）
  • ☐ 写代码前：写完整 demo 脚本（一句话问题绑到一个具体的人 → before state → trigger → aha moment → close），再反推必须做的功能
  • ☐ 冻结 scope，只定一个核心功能。禁止：登录页、动画、多余页面
  • ☐ 总时长 25% 处：端到端骨架必须跑通，多丑都行。之后只准改好，不准加长
  • ☐ 过半后不换方向。有争议就砍功能，不砍主干
  • ☐ 截止前一天：冻结新功能
  • ☐ 睡眠轮换，绝不全队同时倒
  • ☐ 全程正常 commit（获奖后会被查提交时间线和每人贡献）

🚨 清单 C：Demo 前 60 分钟（最高优先级，按顺序做）

T-60 → T-45 ｜ 锁死

  • ☐ 停止写新功能。现在起只允许改 demo 路径上的 bug
  • ☐ commit + push，确认公开 repo 能被匿名打开
  • ☐ 删掉 README 里 repo 中不存在的功能描述。宁可少写，不能对不上
  • ☐ 把 pitch 里每一句技术宣称指到一个具体文件——指不到的，这句话从 pitch 里删掉

T-45 → T-30 ｜ 兜底四件套

  • ☐ 录一遍完整 demo 屏录（哪怕手机拍屏幕），存本地 + 传云各一份；有时间再录第二遍
  • ☐ 缓存 LLM 响应：把 demo 路径跑一遍存成本地 JSON，写 if (apiFail) return cachedResponse
  • ☐ Mock 掉所有外部服务，所有表单预填好（但你号称最难的那件事必须真跑）
  • ☐ 截图 3 张关键界面放在最后一页隐藏页，网断了直接跳过去讲

T-30 → T-20 ｜ 延迟工程

  • ☐ App 一启动就发一次预热请求（不要等上台点按钮才发）
  • ☐ 确认流式输出已开，首 token 秒出
  • ☐ 给每一次等待写好台词：点击提交的那一刻嘴里立刻开始讲技术亮点，讲完正好出结果。绝不静默
  • ☐ 如果延迟 > 8 秒且没法优化 → 这一段改用预录片段

T-20 → T-10 ｜ 掐表排练

  • ☐ 完整跑 2 遍，用手机秒表掐
  • ☐ 硬指标：90 秒内评委必须看到东西在跑。超了就砍功能，不是砍讲解
  • ☐ 检查 demo 只有一条流。有第二条 → 删掉
  • ☐ 检查第一句：一句话锚点（为 Y 做 X 的工具），然后才是问题场景
  • ☐ 时间配比：问题 30% / 方案 70%
  • ☐ 大声排练开场 30 秒（不是整场，就开场）
  • ☐ 准备一句诚实边界："这块现在还是 mock 的，真实实现在 X 文件里"

T-10 → T-5 ｜ Q&A 弹药

  • ☐ 全队对答案：核心那 20% 的逻辑谁写的、怎么工作的
  • ☐ 准备 3 个数字：测试数 / eval 结果 / 延迟或成本。有一个报一个
  • ☐ 背下四个必答题：具体给谁用（具体到一个人）/ 这次具体做了哪部分 / 规模化后最先崩什么 / 下季度谁能真用起来
  • ☐ 准备 30 秒 / 2 分钟 / 5 分钟三个版本的介绍

T-5 → T-0 ｜ 物理检查

  • ☐ 笔记本插电、关通知、关自动更新、分辨率调到投影兼容
  • ☐ 准备手机热点，会场 WiFi 一定会掉
  • ☐ 浏览器只留 demo 需要的标签页
  • ☐ 备份视频在本地能双击播放（不是只在云端）
  • ☐ 让一个人独立复核所有提交材料，对照赛道要求逐项检查
  • ☐ 提前 30 分钟提交——"截止铃响的时候，正是问题出现的时候"

📋 清单 D：线上赛提交页

  • ☐ 用 Devpost 官方 7 段模板，但在顶部先放 Live Demo / Docs 链接
  • ☐ Inspiration 里塞可核查的第三方数据，不是主观感受
  • ☐ How we built it 放架构图
  • ☐ 按主办方要求写清 AI/指定工具的协作过程（OpenAI Build Week 明说这会影响两项打分）
  • ☐ 说出口的每个技术 claim 都能在仓库里找到对应代码
  • ☐ Built With 打全赞助商工具标签
  • ☐ Accomplishments 用可验证运行数据（线上 URL、真实用量、测试数）
  • ☐ 仓库 public（或按规则分享给指定邮箱）+ 赛后保持 public，否则改选他人
